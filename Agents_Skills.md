Reusable procedures for common codebase tasks. Each skill describes **when** to
apply it, **what files** are involved, and the **step-by-step** checklist.

## Skill 1: Assess Whether a Pydantic Field Is Dead Code

**When**: User asks to check if a field can be removed from a node model.

### Key files to inspect

| What | Where |
|------|-------|
| Node model class | `ekg_atos/ekg_atos/schema/stratnav.py`, `common_nodes.py`, `rainbow_review.py` |
| Factory property mappings | Same schema file — `property_mappings` dict in `Neo4jNodeMapping` / `GraphNode` |
| Neo4j factory base | `genai_graph/kg/factories/neo4j_factory.py` — auto-populates `id` from `key_field` |
| Schema generation | `genai_graph/kg/ingest/extract.py` — `metadata_field_names` list skips certain fields |
| Usage in code | Grep `.field_name` across `genai_graph/` and `tests/` |

### Checklist

1. **Check `property_mappings`**: Is the field a target in any mapping? If not, it's never populated from source data.
2. **Check `key_field`**: Is the field used as `key_field`? If so, it's critical — don't remove.
3. **Check `index_fields`**: Is it listed? If so, removing it breaks indexing.
4. **Check `metadata_field_names`** in `extract.py`: Fields like `"id"` are auto-generated by the factory, not read from the Pydantic model.
5. **Grep for `.field_name`**: Any Python code accessing it on model instances?
6. **Verdict**: If the field is not mapped, not used as key/index, and not accessed → safe to remove.

### Common case: the `id` field

The Neo4j factory auto-generates `mapped_props["id"]` from `key_field` (see `neo4j_factory.py`). The field `"id"` is in `metadata_field_names` and excluded from schema column generation. Unless `key_field="id"`, the `id: str` field on a Pydantic model is dead code.

## Skill 2: Merge / Unify Two Node Types Across Factories

**When**: Two factories define semantically identical node types under different names (e.g. `TechnologyPartner` in stratnav and `Partner` in BAML/rainbow_review).

### Decision: choose the canonical name

- The canonical class `__name__` determines the Kuzu table name.
- If one type comes from BAML (auto-generated), the canonical class **must** keep the same `__name__` as the BAML type, because we extend it (like `Customer(BamlCustomer)`).
- So if BAML defines `Partner`, the canonical name is `Partner` — not `TechnologyPartner`.

### Key files to modify

| Step | File | Action |
|------|------|--------|
| 1 | `ekg_atos/ekg_atos/schema/common_nodes.py` | Create canonical class extending BAML type |
| 2 | `ekg_atos/ekg_atos/schema/common_nodes.py` | Add to `get_common_nodes()` with appropriate `key_from` |
| 3 | Factory that defined the old type (e.g. `stratnav.py`) | Delete old class, import canonical from `common_nodes` |
| 4 | Factory that defined the old type | Update `Neo4jNodeMapping.node_class` and `Neo4jRelationMapping.to_node`/`from_node` |
| 5 | Other factories using the type (e.g. `rainbow_review.py`) | Change import from `baml_client.types` to `common_nodes` |
| 6 | Docs: `docs/graph_construction.md` | Update canonical types table and examples |
| 7 | Docs: `docs/baml_extraction_guide.md` | Update Pattern 4 examples |
| 8 | Tests | Run full suite; update test fixtures if they reference the old class name |

### Step-by-step

#### 1. Create canonical type in `common_nodes.py`

```python
from ekg_atos.baml_client.types import Partner as BamlPartner


class Partner(BamlPartner):
    """Partner organization (canonical type for deduplication)."""
```

Pattern: `class <Name>(<BamlName>):` — the `__name__` must match the BAML
type's `__name__` for table unification.

#### 2. Create a `GraphNode` singleton in `canonical_nodes.py`

```python
PartnerNode: GraphNode = GraphNode(
    node_class=Partner,
    name_from="name",
    key_from="name",
    description="Partner organization",
)
```

Export it from the module. Other factories import this singleton.

#### 3–4. Update the factory that owned the old type

- Delete old class definition (e.g. `TechnologyPartner`).
- Add to import: `from ekg_atos.schema.canonical_nodes import ..., PartnerNode`
- Update `Neo4jNodeMapping`: keep `neo4j_label="TechnologyPartner"` (matches source data), change `node_class=Partner`.
- Update `Neo4jRelationMapping`: change `to_node=Partner` (or `from_node`) — these still use raw classes.

#### 5. Update other factories

Replace raw class imports with the node singleton:
```python
# Before
from ekg_atos.baml_client.types import Partner

# ...nodes list...
GraphNode(node_class=Partner, name_from="name", key_from="name")

# After
from ekg_atos.schema.canonical_nodes import PartnerNode

# ...nodes list...
PartnerNode  # use the singleton directly
```

Update any `GraphRelation` calls to pass `PartnerNode` (the `GraphNode` instance) instead of the class.

#### 6–7. Update documentation

- `docs/graph_construction.md` — canonical types table, examples.
- `docs/baml_extraction_guide.md` — Pattern 4 (Cross-Factory Node Unification).

#### 8. Validate

```bash
python -m pytest tests/ -x -q
```

Also verify at runtime:
```python
from ekg_atos.schema.common_nodes import Partner
from ekg_atos.schema.stratnav import StratnavGraph

sg = StratnavGraph.__new__(StratnavGraph)
mapping = [m for m in sg.get_node_mappings() if m.neo4j_label == "TechnologyPartner"][0]
assert mapping.node_class.__name__ == "Partner"
```

## Skill 3: Add a New Node Type to a Neo4j Factory

**When**: A new Neo4j label needs to be imported.

### Checklist

1. **Check if the type already exists** in `common_nodes.py` or BAML types. If yes, import and reuse.
2. **Define Pydantic model** in the factory file (e.g. `stratnav.py`):
   - Use `BaseModel` with `Field(description=...)` for each property.
   - Do NOT add an `id: str` field — the factory auto-generates it from `key_field`.
3. **Add `Neo4jNodeMapping`** in `get_node_mappings()`:
   - `neo4j_label`: exact label string from the Neo4j export.
   - `property_mappings`: `{neo4j_prop: pydantic_field}` — only listed props are imported.
   - `key_field`: field used as PRIMARY KEY (must be in `property_mappings` targets).
   - `name_field`: field used for display name.
   - `index_fields`: fields to index for vector/text search.
4. **Add relationship mappings** in `get_relation_mappings()` if the node participates.
5. **Add the rel type string** to `get_included_rel_types()`.
6. **Update docstring** (node count in class docstring).
7. **Run tests**.

## Skill 4: Add a Field to an Existing Node Type

**When**: A new property from the Neo4j export (or BAML extraction) needs to appear on an existing node.

### For Neo4j factories

1. Add the field to the Pydantic model (with `| None = None` default if optional).
2. Add the mapping in `property_mappings`: `{"neo4jPropertyName": "pydantic_field"}`.
3. If the field should be searchable, add to `index_fields`.
4. Run tests. On next `kg create`, Kuzu will `ALTER TABLE ADD` the new column automatically.

### For BAML factories

1. Add the field to the `.baml` schema file.
2. Run `baml-cli generate` to regenerate `baml_client/`.
3. If the type is extended in `common_nodes.py`, add the field there instead of editing generated code.
4. Run tests.

## Skill 5: Diagnose "Class X Referenced but Has No GraphNode"

**When**: The warning `Class X is referenced in relationships but has no GraphNode` appears during `kg create`.

### Root cause

A `GraphRelation` (or `Neo4jRelationMapping`) references a node class in `from_node` or `to_node`, but no `GraphNode` (or `Neo4jNodeMapping`) is defined for that class.

### Fix options

| Situation | Action |
|-----------|--------|
| Class exists in BAML types and should be a node | Add `GraphNode(node_class=X, ...)` to the schema |
| Class exists but should be unified with another type | Apply **Skill 2** (merge node types) |
| Class is only used as an embedded struct | Remove the relationship; embed the data on the parent node instead |
